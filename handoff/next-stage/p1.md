## Mission 1 — the Machine Continuity Graph

Create one durable history spanning the healthy OS, installed recovery agent, PXE identity, file peer, boots, disks, partitions, filesystems, network interfaces, recovery cases, jobs, artifacts, snapshots, and observed health.

Required behavior:

1. Model these entity types: physical machine, identity alias, boot session, OS installation, agent, disk, partition, volume/filesystem, network interface, snapshot, case, job, artifact, and file set.
2. Preserve relationships across hostname, IP, OS reinstall, DHCP, disk path, and boot changes.
3. Correlate identities using stable machine IDs, DMI UUID, serials, WW peer IDs, physical MACs, disk IDs, and explicit operator aliases. Record confidence and evidence; do not silently merge ambiguous machines.
4. Ingestion is idempotent. Replayed events and inventories cannot duplicate history.
5. Store every inventory version instead of overwriting the previous version.
6. Produce semantic diffs: hardware added/removed, disk health changed, filesystem changed, boot changed, software/OS metadata changed, and agent capability changed.
7. Support indexed time-range, entity, machine, case, disk, text, and health searches without scanning every raw file for every query.
8. Maintain append-only source events plus rebuildable indexes. Abrupt process death may lose at most the currently unflushed record and must not corrupt prior state.
9. Compaction must preserve canonical history and remain restart-safe.
10. Make filesystem state relocatable through an explicit root path for tests, portable installs, and removable recovery media.

Use the simplest storage that meets the performance and durability gates. A compact SQLite index plus immutable files is acceptable if the installed Node runtime supports it without changing shared package files. JSONL plus durable indexes is also acceptable. Do not create a database abstraction zoo.

## Mission 2 — the recovery vault

Build a real data repository, not another file-copy helper.

Required behavior:

1. Content-address every stored object with SHA-256 and deduplicate identical content globally.
2. Chunk large files and disk images so changed regions do not duplicate the whole object. Use deterministic chunking with bounded memory.
3. Store immutable snapshot manifests for files, directory trees, artifacts, sparse images, and arbitrary streams.
4. Preserve file metadata needed for useful restore: relative path, size, times, mode, ownership where supported, sparse regions when detectable, and content chunks.
5. Support interrupted ingest and restore with durable checkpoints and exact resume offsets.
6. Restore one file, a subtree, a complete snapshot, or a streamed image.
7. Compare snapshots by path, metadata, and content identity.
8. Implement repository scrub that verifies manifests, objects, hashes, reference reachability, and missing/corrupt content.
9. Implement explicit retention and pruning: keep-last, hourly/daily/weekly buckets, pinned snapshots, dry report, then actual prune. No hidden automatic deletion.
10. Provide a filesystem backend that works on local disks, mounted NAS paths, and removable media. Keep the backend contract small enough for later object-store adapters, but do not build cloud integrations now.
11. Support importing existing WorkWire recovery artifacts without copying duplicate bytes.
12. Expose repository capacity, unique bytes, logical bytes, dedup ratio, object count, snapshot count, incomplete operations, and last scrub result.

Encryption is deliberately out of scope. Hashing exists for content identity and corruption detection, not as a security project.

## Mission 3 — health intelligence

Turn historical inventory into actionable machine knowledge.

Required behavior:

1. Normalize and retain time series for SMART/NVMe health, temperature, media errors, wear, unsafe shutdowns, disk capacity, filesystem usage, RAID state, boot identity, kernel/storage warnings, agent reachability, and tool coverage when those facts are present.
2. Detect meaningful deltas, worsening trends, sudden device disappearance, identity drift, recurring boot failures, capacity exhaustion, and stale observations.
3. Produce evidence-backed findings with severity, observed values, trend, affected entity, and recommended next operation.
4. Generate powerful recommendations such as snapshot-now, collect-full-inventory, run-long-SMART-test, prepare-ddrescue, verify-vault, or replace-disk. P1 recommends; P3 decides and executes.
5. Rules must be ordinary versioned data, understandable in tests, and overrideable. Do not build a generic policy language.
6. Never claim a failure from one absent optional metric. Report unknown honestly.
