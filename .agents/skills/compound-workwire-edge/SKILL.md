# Compound WorkWire Edge

Choose the move that compounds WorkWire capability, operator control, fleet
reliability, and recovery truth. Turn broad ambition into one defensible
allocation and a proof-bearing execution target.

## Operate inside WorkWire authority

Apply this skill inside the lifecycle established by `pursue-workwire-goals`.
Do not create a second first pass, clarification gate, plan, queue, or handoff
document. Read `AGENTS.md`, then `docs/AGENT-OPERATIONS.md`, then the smallest
relevant contract, affected code, and tests.

Treat code, tests, fresh measurements, live inventory, and authoritative
service state as stronger than prose or enthusiasm. Preserve the current
worktree and account for active changes. Never expose secrets or infer a
machine, disk, privilege, service identity, or release state from a hostname,
cached address, directory name, task registration, or exit code alone.

During the shared read-only first pass, use existing local evidence. Defer
remote mutation, browser sessions, long-running work, and external effects
until the lifecycle closes its one early gate. Remain the allocation
specialist; let `pursue-workwire-goals` own state, mutation, recovery,
preservation, and handoff.

## Frame the allocation

State the desired operator outcome in one sentence. Name the decision horizon,
beneficiary, current baseline, and invariant that must remain true.

Separate the terminal outcome from a proposed implementation. Resolve names,
paths, commands, contracts, and existing failure modes from the repository
before comparing initiatives. Ask only at the shared early gate when a
remaining choice changes authority, target machine, disk, destructive scope,
credential boundary, release, or another hard boundary.

## Build an honest candidate set

Generate a small set of materially different moves from current product truth,
failures, measurements, unfinished work, and recent history. Include repair or
completion of an existing bottleneck when it can dominate new construction.
Include a reversible fixture or benchmark when the key uncertainty can be
bought down cheaply.

Exclude cosmetic variants, unsupported novelty, duplicate control planes, and
work that cannot affect the requested outcome. Reject candidates that cross
device identity, path-containment, credential, data-integrity, service-auth,
licensing, or destructive-irreversibility gates. Do not reject a candidate
merely because it is difficult or large.

Treat a new coordinator, meta-skill, abstraction, service, or control plane as
a candidate only when it owns a distinct trigger, non-duplicated workflow or
knowledge boundary, independently testable output, and lower total
coordination cost than composing what already exists. Prefer strengthening an
existing owner when a new layer would only rename, wrap, or sequence it.

## Rank for compounding leverage

Read [references/decision-contract.md](references/decision-contract.md) when
more than one viable move remains or evidence is mixed.

Compare ranges for expected operator impact, strategic fit, evidence
confidence, durability, compounding, cost of delay, time to decisive proof,
implementation cost, reversibility, downside, and truth risk. Penalize moves
that add operational drag, duplicate a working path, widen an unproved trust
boundary, or defer the core uncertainty. Reward moves that remove a binding
constraint, improve several downstream decisions, create reusable recovery or
verification infrastructure, or make later failures cheaper and safer.

Vary the weakest important assumption. If the winner changes, choose the
cheapest decisive experiment. Prefer the more reversible move when candidates
are otherwise close. Never hide uncertainty behind a decorative total score.

## Commit to one decision

Select one initiative. Name the strongest rejected alternative and the decisive
reason it lost. Define the proof contract before implementation:

- State the baseline and evidence source.
- State the expected observable change.
- State the safety, identity, data, and contract invariants.
- State the narrow positive proof and required negative behavior.
- State the kill, pivot, or rollback condition.
- State the first reversible action.

Do not call an idea an edge before representative WorkWire evidence supports it.
Do not confuse code volume, feature count, benchmark activity, or passing
happy-path output with durable value. Return one bounded decision packet with
the target, baseline, mechanism, evidence class, expected change, invariants,
positive proof, negative proof, kill condition, rollback, and first action.

## Drive the chosen move

When the user requested a decision only, contribute the decision packet to the
sole `pursue-workwire-goals` handoff. When the user requested change, build,
fix, finish, optimize, deploy, install, or equivalent execution, hand the
bounded packet to that lifecycle and continue through implementation and
verification. Do not stop at a ranked list or strategy memo.

Update only the owning WorkWire contract or queue when unfinished work truly
changes. Keep temporary reasoning in task state. Preserve conflict copies and
protected material; never make them runtime inputs or shipped artifacts.

Finish with the owning behavior, affected client or contract parity, narrow
proof, `git diff --check`, and the repository-appropriate test or structure
check.

## Report the operator decision

Lead with the selected move. Report the decisive evidence and strongest
rejected alternative. Report the proof contract and kill condition. Report the
achieved result when execution was in scope. Name one concrete hard stop only
when safe local alternatives are exhausted.
